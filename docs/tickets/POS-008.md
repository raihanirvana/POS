# POS-008 — Kasir React dan pembayaran

Status: Selesai
Prioritas: P0
Dependensi: POS-005, POS-006

## Tujuan

Port menu, pencarian/kategori, pesanan, diskon, checkout tunai/QRIS simulasi ke API transaksi.

## Kriteria penerimaan

- [x] Menu diambil dari API; keranjang dipisahkan dari data domain server.
- [x] Panel pesanan desktop/mobile mendukung jumlah, hapus, pelanggan, dan jenis pesanan.
- [x] Tombol konfirmasi menahan submit ganda; idempotency key dipertahankan saat retry jaringan.
- [x] Preview total di frontend dan hasil final server konsisten; perubahan harga/stok ditangani.
- [x] Checkout sukses memperbarui stok dan membuka struk; gagal mempertahankan keranjang.
- [x] QRIS tetap jelas simulasi; tidak ada gateway atau QR pembayaran fiktif.

## Verifikasi tanpa unit test

1. Coba alur kasir utuh di desktop dan ponsel.
2. Coba uang kurang, stok berubah, klik ganda, dan retry setelah respons jaringan hilang.

## Implementasi

- **Menu** (`pages/CashierPage.jsx`, `components/cashier/Menu*`): daftar dari `GET /api/products`. Pencarian dan kategori difilter di browser agar instan. Kartu menampilkan foto lokal, label, harga, dan stok; tombol tambah nonaktif saat stok 0 atau jumlah di pesanan sudah sama dengan stok.
- **Keranjang** (`cart/`, `hooks/useCartState.js`, `lib/cart.js`):
  - Hanya menyimpan `productId`, jumlah, dan nama untuk pesan, plus pelanggan, jenis pesanan, dan teks diskon. Harga dan stok selalu dari daftar produk terbaru.
  - Disimpan di context di atas shell, jadi bertahan saat pindah halaman dan hilang saat keluar atau sesi berakhir. Tidak memakai localStorage.
- **Penyesuaian stok:** setiap kali menu dimuat ulang, pesanan disesuaikan dengan stok dan produk terbaru (jumlah diturunkan, item yang hilang atau habis dihapus), disertai pesan yang menjelaskan perubahan.
- **Pratinjau total** memakai rumus server: `round(subtotal × persen / 100)`. Diskon harus bilangan bulat 0–100.
- **Panel pesanan:** di layar >720 px panel menempel di samping. Di ponsel ada bar bawah "Lihat pesanan (n) · total" yang membuka panel sebagai `<dialog>` modal (fokus terkunci, Escape menutup, fokus kembali ke bar); panel tertutup sendiri saat pembayaran dibuka.
- **Pembayaran** (`PaymentDialog`, `usePaymentForm`, `useCheckout`, `usePaymentFlow`):
  - Tunai: nominal, tombol cepat (uang pas, pembulatan), serta kembalian atau kekurangan langsung terlihat.
  - QRIS: teks simulasi saja.
  - Body hanya berisi produk/jumlah, diskon, pelanggan, jenis pesanan, metode, dan uang diterima; harga dan total tidak dikirim.
- **Idempotency:**
  - Satu percobaan bayar memakai satu key acak (`crypto.randomUUID`, dengan fallback `getRandomValues`). Klik ganda dicegah oleh guard `ref`, sehingga request kedua tidak sempat dikirim sebelum React render ulang.
  - Hasil tidak pasti (jaringan putus, 5xx, respons rusak) menyimpan key dan body. Pesanan dan input dikunci, lalu tombol menjadi "Kirim ulang pembayaran" dengan key yang sama. Ada juga pilihan membatalkan percobaan dengan peringatan untuk mengecek halaman Transaksi.
  - Penolakan pasti (400/409/403) membuang key sehingga pesanan bisa diperbaiki. 409 stok atau produk memuat ulang menu untuk penyesuaian.
- **Struk** (`components/receipt/`): dari snapshot transaksi server, dengan catatan bila transaksi adalah replay atau bila total final berbeda dari pratinjau karena harga berubah. Cetak dan riwayat dikerjakan POS-009.
- **Bersama:** `DialogHeader`, `useMediaQuery`, `lib/transactions-api.js` (validasi bentuk respons), dan format tanggal/label di `lib/format.js`.

## Review dan perbaikan

Review pada 15 Oktober 2026 melalui Chrome headless/Playwright, build produksi Express, port acak, serta database dan konteks browser sementara. Tidak menambah unit test atau dependency proyek.

- **Retry setelah HTTP 408:** sebelum perbaikan, server yang sudah menyimpan transaksi lalu mendapat respons 408 menyebabkan retry memakai key baru; reproduksi menghasilkan dua transaksi. 408 kini dianggap hasil tidak pasti, key/body dikunci dan dipakai ulang. Uji ulang menghasilkan satu transaksi dan sekali pengurangan stok, dengan struk replay.
- **Struk saat pindah halaman:** hasil checkout yang tiba setelah halaman Kasir ditinggalkan sebelumnya mengosongkan pesanan tanpa menampilkan struk ketika kembali. Snapshot struk sekarang disimpan bersama context keranjang sampai ditutup, sehingga tetap muncul setelah kembali ke Kasir.
- **Pratinjau percobaan tertunda:** total awal disimpan sebagai metadata lokal percobaan, tanpa dikirim ke server. Saat menu berubah dari 22.000 → 30.000 sebelum transaksi lalu 40.000 sebelum replay, struk tetap membandingkan hasil final 30.000 dengan pratinjau awal 22.000. Key/body tidak berubah.
- **Pesanan menjadi kosong:** setelah produk terakhir dihapus/habis dan server menolak 409, konfirmasi sebelumnya masih aktif. Kini pesanan kosong tidak bisa dibayar; pesan mengarahkan pengguna menutup pembayaran lalu memilih menu kembali. Diskon 100% dengan item valid tetap bisa dibayar.
- **Respons transaksi rusak:** alamat/pesan toko berbentuk objek sebelumnya membuat React crash sesudah key dibuang. Validasi sekarang memeriksa seluruh teks struk yang dirender, tanggal, batas harga/jumlah/uang, serta kesesuaian subtotal, diskon, total, dan kembalian. Enam respons rusak diuji; semuanya mempertahankan key sebagai hasil tidak pasti dan berhasil dipulihkan lewat replay tanpa transaksi ganda.
- **Nominal/error tunai:** nominal di atas Rp1 triliun ditolak sebelum request. Koreksi nominal/metode setelah penolakan pasti menghapus error lama; `aria-invalid` mengikuti input dan error server. Pesan field non-string tidak dirender, sementara detail field yang valid tetap ditampilkan. Uang diterima 0 dipulihkan dengan benar saat pembayaran diskon 100% dibuka ulang.
- **Regresi checkout nyata:** contoh PRD 72.000/kembalian 28.000, diskon invalid, uang kurang, dua submit dalam satu event, Escape saat sibuk, kehilangan respons setelah server menyimpan, QRIS simulasi, perubahan stok/harga, serta 400/401 lolos. Body tidak membawa harga, total, atau metadata pratinjau.
- **Stok:** pesanan 3 Cinnamon Roll disesuaikan ke 1 setelah 409. Produk terakhir yang dihapus mengosongkan pesanan dengan konfirmasi nonaktif. Checkout sukses mengosongkan pesanan dan memperbarui stok; sesi dicabut saat bayar menambah nol transaksi.
- **Mobile/visual:** dialog pesanan 360px mempertahankan fokus, Escape kembali ke bar pesanan, dan perpindahan ke pembayaran tidak meninggalkan dialog bertumpuk. QRIS tidak memiliki gambar/canvas pembayaran. Struk 360px serta panel 768px muat tanpa overflow; screenshot desktop dan struk ponsel diperiksa.
- Regresi POS-006 (sesi, peran, logout, redirect, error/retry, keyboard) dan POS-007 (CRUD, stok bersamaan, snapshot, validasi, respons rusak, refresh/restart) lolos pada database baru.
- Tidak ada `pageerror` browser atau error 500 nyata dari API. `integrity_check`, `foreign_key_check`, stok nonnegatif, `npm run check`, dan aturan maksimal 25 baris per fungsi lolos. Respons gagal sengaja disimulasikan di browser; penjualan dan stok tetap diperiksa di SQLite asli.

Batas tahap ini:

- Pesanan hanya di memori tab. Refresh browser atau sesi berakhir mengosongkan pesanan, termasuk percobaan bayar yang belum pasti. Setelah refresh, cek halaman Transaksi (POS-009) sebelum membuat pesanan ulang.
- Menu kasir tidak memuat ulang otomatis. Stok dari kasir lain baru terlihat setelah checkout, setelah respons 409, atau setelah halaman dimuat ulang.
- Screenshot `fullPage` setelah halaman tergulir menggambar sidebar `fixed` di posisi gulir; itu artefak alat screenshot, bukan tampilan browser. Screenshot viewport normal.
- Cetak struk, riwayat, dan buka ulang struk dikerjakan POS-009.
- Firefox dan Safari belum diuji.
