# POS-005 — API checkout dan transaksi atomik

Status: Selesai
Prioritas: P0
Dependensi: POS-004

## Tujuan

Server menghitung harga/subtotal/diskon/kembalian dan menyimpan penjualan beserta stok dalam satu transaksi SQLite.

## Kriteria penerimaan

- [x] POST /api/transactions menerima produk/jumlah, diskon, pelanggan, metode, dan idempotency key.
- [x] Total/harga/peran dari client tidak dipercaya; server menghitung memakai harga DB terkini.
- [x] Stok dicek dan dikurangi atomik; kegagalan satu item membatalkan seluruh transaksi.
- [x] Uang kurang, qty tidak valid, produk dihapus, diskon di luar 0–100%, dan stok kurang ditolak.
- [x] Replay key yang sama dengan payload sama mengembalikan transaksi yang sama; payload beda mendapat 409.
- [x] GET daftar/detail transaksi dibatasi workspace; item dan pengaturan struk disnapshot.

## Verifikasi tanpa unit test

1. Coba contoh PRD: 2 kopi + croissant, diskon 10%, bayar Rp100.000 menghasilkan total Rp72.000/kembalian Rp28.000.
2. Kirim dua checkout untuk stok terakhir: hanya satu berhasil.
3. Ulangi request dengan key sama; stok dan jumlah transaksi tidak berubah dua kali.
4. Coba satu item kehabisan stok; item lain juga tidak berkurang.

## Implementasi

- `server/services/transaction-service.js`: checkout dalam satu `withWorkspaceAccess` (`BEGIN IMMEDIATE`). Urutannya:
  1. Sesi diperiksa ulang.
  2. Replay dicek dengan `request_hash` (SHA-256 payload ternormalisasi).
  3. Harga dibaca dari DB, lalu total dan pembayaran dihitung.
  4. Nomor `SDH-YYYYMMDD-NNN` (hari Jakarta) dan snapshot toko dibuat.
  5. Stok dikurangi bersyarat.
  6. Transaksi, item, dan snapshot toko disimpan.
- `server/services/transaction-query-service.js`: daftar (cari nomor/pelanggan, tanggal Jakarta, limit/offset) dan detail.
- `server/validation/transaction-validation.js`: field asing (`total`, `unitPrice`, `cashierRole`, `workspaceId`) ditolak; QRIS tidak menerima `amountReceived`.
- `server/repositories/transaction-repository.js` dan `settings-repository.js`: query berparameter dan selalu memakai `workspace_id`.
- `server/services/workspace-access.js` menggantikan `product-access.js`. Pemeriksaan ulang sesi di dalam transaksi kini dipakai produk (pemilik) dan checkout (kasir/pemilik).
- Helper bersama: `assertJsonObject`, `isUuid` (`validation/common.js`), `likePattern` (`repositories/sql.js`), dan `formatRupiah` (`lib/money.js`).

## Bukti selesai

Verifikasi pada 15 Oktober 2026 dengan Node 22.20.0, memakai database sementara serta port 3031/3032 sehingga `data/seduh.sqlite` tidak tersentuh. Sesi: pemilik A, pemilik B, dan kasir C.

- **Contoh PRD** (kasir C): 2 Kopi Susu Seduh + 1 Butter Croissant, diskon 10%, tunai Rp100.000 → 201 `SDH-20261015-001`. Hasilnya subtotal 80.000, diskon 8.000, total 72.000, kembalian 28.000, dan `cashierRole: cashier`. Stok berubah 35→33 dan 18→17. Nama `"  Raka "` di-trim.
- **Idempotensi:** replay body yang sama → 200 `replayed: true`, ID dan nomor sama, stok tetap. Key sama dengan diskon 20% → 409 `IDEMPOTENCY_CONFLICT`; hanya 1 transaksi untuk key itu.
- **QRIS** tanpa `amountReceived` → 201. Nama kosong menjadi `Pelanggan`, `amountReceived = total`, kembalian 0.
- **Input invalid:** 24 body ditolak 400 tanpa mengubah jumlah transaksi (92) atau stok:
  - uang kurang (`Uang kurang Rp4.000. Minimal Rp84.000.`);
  - qty 0, −1, 1.5, string, dan 100.001; produk ganda; items kosong; 51 item;
  - `unitPrice` di item; `total`/`subtotal` di body; `cashierRole`/`workspaceId` di body;
  - diskon 101, −1, dan 10.5; productId rusak;
  - tanpa key; key berisi spasi/garis miring;
  - QRIS dengan `amountReceived`; tunai tanpa uang; uang berupa string;
  - metode/jenis pesanan asing; nama 61 karakter; body array.
- **Produk tidak tersedia:** A menghapus Lemon Tea lalu checkout Lemon Tea + Americano → 409 `PRODUCT_UNAVAILABLE`. Produk milik workspace C dipakai A → 409 yang sama, tanpa membocorkan keberadaannya.
- **Atomik:** Americano 3 + Cinnamon Roll 9 (stok 8) → 409 `INSUFFICIENT_STOCK` "Stok Cinnamon Roll tinggal 8". Americano tetap 40, Cinnamon Roll tetap 8.
- **Stok terakhir, dua proses API** (port 3031 dan 3032 pada DB yang sama): stok diset 1, lalu 6 checkout paralel dengan key berbeda. Hasilnya 1×201 dan 5×409, stok akhir 0, dan hanya 1 item tersimpan.
- **Key sama paralel** di dua proses (4 request): 1×201 + 3×200 `replayed: true` dengan nomor sama. Stok 5→4 dan hanya 1 transaksi.
- **Snapshot:**
  - Harga Americano diubah ke 25.000 dan `settings.store_name` ke "Seduh Baru" (langsung di SQLite, karena API pengaturan baru ada di POS-011). Checkout 2× diskon 15% menghasilkan subtotal 50.000, diskon 7.500, total 42.500, toko "Seduh Baru", dan peran owner.
  - Setelah harga diubah lagi ke 30.000, detail transaksi itu tetap 25.000.
  - Transaksi PRD lama di workspace C tetap "Seduh Coffee".
- **Daftar/detail** (kasir C):
  - Semua → 32 transaksi, terbaru dulu, dengan `itemCount`.
  - Cari `raka` → 7; cari nomor `SDH-20261015` → 2; `date=2026-10-15` → 2; `date=2026-10-14` → 5.
  - `limit=2&offset=1` benar. `search=%` → 0.
  - `date=2026-02-30` dan `limit=0` → 400 dengan `fields`.
  - B membuka detail milik C → 404, dan daftar B tidak memuat transaksi C.
  - Tanpa sesi → 401, ID rusak → 404.
- **Sesi dicabut:** C ganti peran ke owner. Checkout dengan cookie lama → 401 `UNAUTHENTICATED`; cookie baru → 201.
- **Restart API:** daftar transaksi dan produk A identik (hash respons sama).
- **Integritas:** `foreign_key_check` kosong, `integrity_check` ok. Semua transaksi memenuhi `subtotal = Σ line_total`. Tidak ada stok negatif. Detail item memakai `transaction_items_transaction_idx`. Log kedua API tanpa error 500.
- `npm run check` (lint, format, build) dan `git diff --check` lolos.

## Review dan verifikasi ulang

Review pada 15 Oktober 2026 memakai dua proses API pada port acak dan database sementara. Tidak menambahkan unit test atau menyentuh database pengembangan.

- Memperbaiki filter tanggal: bulan/hari tidak valid sebelumnya melempar `RangeError` dan menghasilkan 500; sekarang 400 `VALIDATION_ERROR` dengan `fields.date`. Rentang Jakarta pada batas tahun 0000/9999 juga memakai batas ISO empat digit yang sesuai SQLite.
- Memperbaiki QRIS yang sebelumnya menerima `amountReceived: null`; sekarang field itu ditolak 400 sesuai kontrak.
- Contoh PRD kembali menghasilkan subtotal 80.000, diskon 8.000, total 72.000, dan kembalian 28.000. Replay nama yang sudah di-trim mengembalikan ID/nomor sama tanpa pengurangan stok lagi.
- **36 payload invalid** ditolak 400 tanpa perubahan stok, header transaksi, atau item; QRIS dengan diskon 100% berhasil dengan total/kembalian 0.
- **Rollback setelah sebagian INSERT:** trigger sementara menggagalkan item kedua setelah stok dan item pertama berubah. Respons 500, seluruh perubahan dibatalkan. Setelah trigger dihapus, retry key yang sama berhasil 201. Ini satu-satunya error 500 pada verifikasi ulang, sengaja dipicu untuk memeriksa rollback.
- **Dua proses API:** enam checkout stok terakhir menghasilkan 1×201 dan 5×409. Empat retry paralel dengan key sama menghasilkan 1×201 dan 3×200, dengan satu ID transaksi dan sekali pengurangan stok.
- Harga database terkini dan pembulatan diskon benar; detail serta replay tetap mempertahankan snapshot setelah harga/toko berubah dan produk dihapus (`productId` menjadi `null`). Produk workspace asing ditolak 409 dan detail asing 404.
- Tanggal kabisat, bulan/hari invalid, batas tahun 0000/9999 dengan transaksi nyata, filter hari Jakarta, pencarian, pagination, dan penolakan tanpa sesi lolos.
- Subtotal tepat Rp1 triliun diterima; subtotal di atas batas mendapat 400 tanpa mutasi. Nomor berlanjut dari akhiran 999 ke 1000.
- Checkout yang menunggu kunci SQLite ditolak 401 setelah sesi dicabut, cookie dihapus, dan tidak mengubah data. Restart mempertahankan daftar transaksi.
- Regresi POS-004 lolos: CRUD, validasi Unicode, peran kasir, isolasi, snapshot, restart, serta POST/PATCH/DELETE yang menunggu setelah pencabutan sesi.
- `integrity_check`, `foreign_key_check`, kesesuaian subtotal dengan jumlah item, stok nonnegatif, dan `npm run check` lolos. Aturan fungsi maksimal 25 baris tetap aktif.

Batas tahap ini:

- Pembayaran tetap simulasi; QRIS tidak menghubungi payment gateway.
- Idempotency key disimpan selamanya selama workspace ada. Request gagal (400/409) tidak menyimpan key sehingga bisa dicoba lagi.
- Produk yang sama tidak boleh muncul dua kali dalam satu pesanan; frontend menggabungkan jumlahnya.
- Pencarian transaksi tidak peka huruf besar/kecil hanya untuk huruf ASCII.
- Snapshot pengaturan diuji dengan mengubah SQLite langsung; uji lewat API pengaturan dilakukan di POS-011.
- Struk dan riwayat di UI dikerjakan POS-008/POS-009.
