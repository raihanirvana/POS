# POS-011 — Pengaturan kedai dan reset ruang demo

Status: Selesai
Prioritas: P1
Dependensi: POS-007, POS-009, POS-010

## Tujuan

Pengaturan toko lewat API pemilik dan reset yang hanya memengaruhi ruang demo pengunjung.

## Kriteria penerimaan

- [x] Nama/alamat/pesan struk divalidasi dan disimpan per workspace.
- [x] Reset memerlukan konfirmasi serta berjalan atomik pada workspace terkait.
- [x] Reset membatalkan keranjang di frontend dan mengembalikan seed; workspace lain tidak berubah.
- [x] Struk yang sudah tersimpan memakai snapshot pengaturan saat penjualan.
- [x] Kasir tidak bisa mengubah pengaturan/reset lewat API.

## Verifikasi tanpa unit test

1. Ubah pengaturan, buat transaksi, ubah lagi, dan periksa struk.
2. Reset di browser A; data browser B tetap utuh; uji pembatasan kasir.

## Implementasi

**Server** (`routes/settings.js`):

- `GET /api/settings` untuk kasir dan pemilik.
- `PATCH /api/settings` khusus pemilik, dengan validasi `validation/settings-validation.js`: batas 60/150/200 karakter Unicode, karakter kontrol ditolak, field asing atau body kosong 400. Kolom UPDATE berasal dari daftar tetap di `settings-repository.js`.
- `POST /api/demo/reset` khusus pemilik, wajib body `{"confirmation":"reset"}`.
  - `resetWorkspace` dijalankan dalam `withOwnerWorkspace` (`BEGIN IMMEDIATE` + sesi diperiksa ulang): `clearWorkspaceData` menghapus transaksi (item ikut CASCADE), produk, dan pengaturan workspace sesi, mengosongkan `seeded_at`, lalu `seedWorkspaceData`.
  - Sesi tidak disentuh.
- Pesan 403 dari pemeriksaan ulang pemilik dibuat umum ("Hanya pemilik dapat melakukan perubahan ini."), karena kini dipakai produk, pengaturan, dan reset.

**Client** (`/pengaturan`, pemilik):

- Form identitas kedai (`SettingsForm`, `useSettingsForm`, `lib/settings-form.js`):
  - Nama, alamat, dan pesan struk (textarea) dengan label, penghitung "n/batas karakter", dan validasi klien yang sama dengan server; fokus pindah ke field salah.
  - Hanya field yang berubah dikirim; tanpa perubahan tidak ada request. Fieldset dikunci saat menyimpan, reset, dan pemuatan ulang pengaturan. Tombol reset nonaktif selama penyimpanan di halaman ini.
  - Error server tampil per field atau sebagai notice. Setelah simpan, data dimuat ulang dari server dan form dipasang ulang.
- Zona reset (`ResetPanel`, `useDemoReset`):
  - `ConfirmDialog` menjelaskan data yang diganti dan bahwa ruang demo lain tidak berubah. Escape membatalkan; error tampil di dalam dialog dengan "Coba reset lagi".
  - Selama request reset berjalan, kunci di CartProvider mencegah perubahan keranjang, checkout, dan reset kedua, termasuk setelah pindah halaman. Setelah berhasil, `cart.resetAll()` mengosongkan pesanan, membatalkan percobaan bayar (key dibuang karena produk lama sudah hilang), dan menutup struk tertunda. Respons checkout yang datang setelah pembatalan diabaikan. Pengaturan lalu dimuat ulang.

## Bukti selesai

Verifikasi pada 15 Oktober 2026 dengan build produksi (`npm start`, database sementara) memakai curl, SQL via `node:sqlite`, dan Google Chrome headless melalui Playwright (`playwright-core` dari cache npx, di luar repo). Tidak ada dependency atau file uji di repo.

**API** (port 3091):

- GET settings: pemilik dan kasir 200, tanpa sesi 401.
- PATCH `"  Seduh Senopati  "` + pesan baru → 200 dengan nama di-trim. Invalid → 400 dengan `fields`:
  - nama kosong, alamat 151 karakter, dan pesan berisi NUL sekaligus;
  - `{}`; field `workspaceId`; nama berupa angka.
- Kasir PATCH → 403. Pengaturan workspace B tidak berubah.
- **Snapshot:** transaksi dibuat saat toko "Seduh Senopati", lalu toko diganti "Seduh Kemang" + alamat baru. Detail transaksi tetap "Seduh Senopati | Jl. Melati No. 12, Jakarta | Sampai jumpa lagi!".
- Reset dengan `{}`, `{"confirmation":"yes"}`, atau tanpa body → 400. Kasir → 403.
- **Rollback:** trigger SQLite sementara menggagalkan insert seed produk ke-9 → reset 500. Workspace A tetap 9 produk, 31 transaksi, toko "Seduh Kemang", dan `seeded_at` terisi; trigger lalu dihapus.
- **Reset berhasil** → `{"reset":true,"products":9,"transactions":30}`:
  - A kembali 9 produk, 30 transaksi, "Seduh Coffee"; menu percobaan hilang; sesi A tetap 200.
  - B tetap 9/30.
  - Replay idempotency key lama dengan produk lama → 409 `PRODUCT_UNAVAILABLE`.
  - `foreign_key_check` kosong dan `integrity_check` ok.
- **Isolasi dengan B yang sudah diubah** (port 3092): B berisi "Kedai B", 10 produk, 31 transaksi, dan stok Menu Khusus B = 2. Setelah A reset, nilai B identik.

**Browser** (port 3092):

- Form awal "Seduh Coffee", "12/60 karakter". Nama kosong → pesan error, fokus `settings-storeName`, dan 0 PATCH.
- Simpan → "Pengaturan disimpan." dengan body PATCH hanya `{"storeName":"Seduh Senopati","receiptMessage":"Sampai jumpa di Senopati!"}`. Nilai tetap setelah refresh.
- Transaksi dibuat, lalu nama diganti "Seduh Kemang" → struk transaksi itu di `/transaksi` tetap "Seduh Senopati" dengan pesan "Sampai jumpa di Senopati!".
- Kasir berisi Americano dengan pembayaran QRIS yang belum pasti (respons diputus) → pesanan terkunci dengan tombol "Lanjutkan pembayaran tertunda".
- Di Pengaturan, dialog reset dibatalkan dengan Escape (nama tetap "Seduh Kemang"). Reset 500 tersimulasi → "Reset belum berhasil … Kode permintaan: r-reset". "Coba reset lagi" → "Data contoh dipulihkan: 9 menu dan 30 transaksi. Pesanan di Kasir dibatalkan." dan form "Seduh Coffee".
- Kembali ke Kasir: "Mulai dengan memilih menu", tombol tambah aktif, "Lanjut pembayaran", tanpa peringatan tertunda.
- Kasir di `/pengaturan` → halaman 403. Lewat API: PATCH 403, reset 403, GET 200.
- 360px tanpa overflow. Screenshot desktop diperiksa visual.
- Tidak ada `pageerror`. Satu-satunya error 500 di log berasal dari uji rollback trigger yang disengaja.

## Review dan perbaikan — 15 Oktober 2026

- **Checkout terlambat setelah reset:** pembayaran sudah tercatat, lalu responsnya ditunda; pengguna kembali lewat browser Back, reset, dan membuat pesanan baru. Sebelumnya respons lama menghapus pesanan baru dan memunculkan struk transaksi yang sudah dihapus. `useCheckout` sekarang mengidentifikasi request aktif; pembatalan mengabaikan respons lama dan pembayaran baru dapat berjalan tanpa menunggu request lama.
- **Reset saat pindah halaman:** kunci reset disimpan bersama keranjang di CartProvider. Tombol tambah, perubahan pesanan, dan checkout dikunci sampai request selesai; kegagalan tidak menghapus keranjang. Request reset ganda diblokir dengan ref, bukan hanya status tombol.
- **Simpan dan reset pada halaman pengaturan:** reset nonaktif selama PATCH, editor nonaktif selama reset atau GET pemuatan ulang. Ini mencegah reset bertabrakan dengan penyimpanan dan perubahan pengguna hilang karena form dipasang ulang saat data terbaru tiba. Submit ganda diblokir; error field dari server memperoleh fokus setelah editor dibuka kembali.
- **Respons invalid:** timestamp dan batas teks pengaturan divalidasi; jumlah menu/transaksi reset wajib integer dengan batas yang benar. Payload rusak menampilkan error yang dapat dicoba lagi, bukan pesan berhasil seperti `[object Object]`. Validasi klien juga menolak Unicode dengan surrogate tidak berpasangan.

Verifikasi review memakai build produksi, SQLite/port sementara dan Chrome melalui Playwright, tanpa unit test atau dependency baru:

- Respons sukses checkout sebelum reset yang ditunda tidak membuka struk lama atau menghapus satu item pesanan baru. Respons gagal checkout lama tidak mengunci pembayaran baru yang sudah berhasil.
- Saat reset tertunda dan pengguna browser Back ke Kasir, keranjang/checkout tetap terkunci dan pesan reset tampil; setelah berhasil pesanan kosong dan menu aktif. Dua klik pada konfirmasi mengirim satu POST; Escape dan Batal tidak menutup dialog yang sedang memproses.
- API menerima batas tepat 60/150/200 karakter Unicode dan menolak input kosong, berlebih, kontrol, surrogate, tipe salah, serta field asing. Perubahan toko setelah penjualan tidak mengubah snapshot struk.
- Trigger pada seed Cinnamon Roll menghasilkan 500 yang disengaja; seluruh produk, transaksi/item, pengaturan, dan `seeded_at` A kembali persis. Setelah trigger dihapus, reset mengganti ID produk, memulihkan seed dan pengaturan, mempertahankan sesi/expiry, serta tidak mengubah workspace B yang sudah dikustomisasi.
- Checkout dengan produk lama sesudah reset mendapat 409 dan detail transaksi yang dihapus mendapat 404. Kasir/header peran palsu tetap 403, tanpa sesi 401.
- PATCH/reset yang menunggu kunci tulis memeriksa ulang sesi: token dicabut → 401, peran diubah jadi kasir → 403, sesi berakhir → 401; tidak ada data domain yang berubah.
- Submit tanpa perubahan mengirim nol PATCH; validasi klien memfokuskan nama kosong dan menolak 61 emoji; PATCH hanya berisi field yang berubah. Editor/reset terkunci selama GET setelah simpan, kemudian nilainya benar setelah refresh.
- Lima respons pengaturan rusak dan lima respons reset rusak menampilkan error; Coba lagi memulihkan pengaturan. Error field server yang berupa objek diabaikan, dan field valid mendapat fokus. Reset gagal koneksi dapat dicoba ulang; 401 pada simpan mengembalikan pengguna ke masuk.
- Form/dialog tanpa overflow pada 360/768/1280px; Escape mengembalikan fokus ke tombol reset. Screenshot diperiksa visual. Integritas SQLite dan foreign key lolos, tanpa `pageerror`.
- Regresi POS-007, POS-008, dan POS-010 dijalankan ulang dan lolos. `npm run check` (termasuk maksimal 25 baris per fungsi) dan `git diff --check` lolos.

Batas tahap ini:

- Reset hanya membatalkan keranjang di tab yang melakukan reset. Tab atau kasir lain di workspace sama akan menerima 409 produk tidak tersedia saat checkout, lalu menunya dimuat ulang.
- Nama toko belum tampil di sidebar atau breadcrumb; identitas toko tampil di struk.
- Jika koneksi terputus sesudah reset sudah di-commit, Coba reset lagi menjalankan reset baru; endpoint reset belum memakai idempotency key.
- Firefox dan Safari belum diuji.
